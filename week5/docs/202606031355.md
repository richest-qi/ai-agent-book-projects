一个基础的Coding Agent需要配备以下7个核心工具：  
- Code Interpreter（代码解释器）
- Bash Shell（命令行终端）
- 读文件工具
- 写文件工具
- 编辑文件工具
- 搜索文件名工具（Glob）
- 搜索文件内容工具（Grep）   

 每个通用Agent都应该具备coding能力。即使你的Agent主要用于某个垂直领域，为其配备基本的coding能力也会显著提升其问题解决的灵活性。  

 ## Coding Agent的整体流程
 - 项目文档化   
    Agent首先建立对整个项目的认知框架：通过系统性地阅读代码库，识别出项目的主要模块、核心抽象、以及各组件之间的依赖关系。基于这些理解，Agent生成包含架构设计概览、主要目录结构说明、以及测试运行指南等文档。
- 任务理解与需求澄清   
    面对用户提出的需求，Agent需要首先判断其复杂度和明确性。       
    对于复杂需求：需求本身的模糊性（用户知道想要什么，但无法精确表达）、实现路径的多样性（有多种技术方案可选，各有权衡）、或是影响范围的广泛性（需要修改多个模块、可能破坏现有功能），面对这类任务，Agent第一步是**通过探索性调研来澄清需求的边界**。如果用户的描述过于抽象或存在内在矛盾，Agent应该主动发起与用户的对话，提出针对性问题来揭示隐藏的假设和约束。  
    例如：当用户要求“优化系统性能”时，Agent需要了解优化的具体目标（是降低响应时间、减少内存占用、还是提高吞吐量）、可接受的权衡（是否允许增加代码复杂度）、以及性能基准（当前的瓶颈在哪里），这个澄清至关重要，因为在需求模糊的状态下开始编码，往往导致大量的返工和资源浪费。   
- 编写设计文档  
    编写设计文档的过程本身就是一次深度思考，Agent在投入大量编码工作之前，先在概念层面上验证方案的可行性。在Agent完成设计文档后，主动将其提交给用户进行审查，等待明确的批准信号后再继续前进。   
    设计文档应该回答几个核心问题：    
    - 将要修改哪些模块？为什么选择这些模块？
    - 采用什么技术方案？这个方案相比其他备选方案有何优势？
    - 需要引入哪些新的抽象或依赖，这些引入是否合理？
    - 预期会对系统的其他部分产生什么影响，如何管理这些影响
- 代码实现与测试   
    编码→测试→修复→代码审查→修复
- 文档同步与交付  
    如果代码的修改涉及到架构层面的变化——例如引入了新的模块、改变了模块间的依赖关系、或是修改了核心抽象的语义——Agent需要相应地更新架构设计文档，确保文档与代码保持一致。  


## Coding Agent的实现技巧  
- 并行工具调用与流式执行  
- 上下文的精细化管理    
    代码库通常非常庞大，但模型的上下文窗口是有限的。智能的上下文管理需要在多个层面展开。  
    - 文件读取层面   
        Agent不应该总是读取文件的全部内容。对于大型文件，工具应该支持按行号范围读取特定片段，这样模型可以先通过搜索工具定位到相关的代码区域，然后仅读取那些区域及其必要的上下文。
    - 命令执行层面
        一个编译过程或测试运行可能产生数千行输出，如果全部注入上下文，会迅速耗尽预算。  
- 环境信息的动态注入  
    当前工作目录是什么，当前git分支是什么，最近的git提交记录，未暂存和已暂存的文件变更概览...这些环境信息不应该被硬编码在静态的系统提示词中——那样会破坏KV Cache的效率——而应该作为动态的、追加式的System Hint，在每次推理时实时生成并注入。   
- 命令执行环境的状态持久化  
    如果每次执行命令都在一个全新的、隔离的Shell中进行，这些状态都会丢失，Agent不得不在每次操作前重复相同的设置步骤。因此，Coding Agent应该维护一个持久化的终端会话。这个终端在Agent启动时创建，并在整个交互过程中保持活跃。每次命令都在这个共享的终端中执行，从而保留了工作目录、环境变量、以及其他会话状态。
- 即时的语法反馈机制  
    当Agent修改代码后，工具层自动运行相应的linter或者语法检查器，并将检查结果作为工具返回值的一部分呈现给Agent。如果检查到语法错误，Agent在下一轮推理中就会立即看到详细的错误信息。  
    这种即时反馈机制就像现代IDE在开发者编写代码的同时提供实时的语法高亮和错误提示一样，显著降低了错误的修复成本，因为Agent可以在错误引入的那一刻就进行修正，而不需要等运行测试或编译时才发现问题。    


## Coding Agent的搜索工具
- 正则表达式内容匹配   
    grep
- 文件名模式匹配
    glob  
- 语义代码搜索  
- 符号级定义与引用查找      
    在庞大的代码库中，很多函数名是重复的，但它们表达的不是一个意思。   
    符号查找的效率更高、更准确，而且能保证找到所有出现的地方，防止修改代码时漏掉一些相关的模块，与前3种方法都是基于文本（无论是字面文本还是向量化的文本）不同，符号搜索能够回答诸如“这个函数在哪里被调用”等问题。
- 搜索策略的组合使用    
    通常是
    1. 先通过 语义搜索 找到大致相关的模块
    2. 再通过 正则表达式搜索 精确定位特定的实现
    3. 最后通过 符号搜索 追踪所有的调用点   

## Coding Agent的文件编辑工具
- 差异字符串与差异应用模型  
    Diff String   
    Apply Diff Model，早期的Cursor采用了这种模式  
- 旧字符串到新字符串 
    Old String to New String
- 行号定位机制  
- 类Vim编辑命令
- 字符串首尾匹配  
    Old String Start + Old String End + New String

## 让Agent编写Agent的关键技巧
- 上下文管理的随意性        
    可能将Agent的执行轨迹简单地转换为纯文本格式塞进上下文，完全忽略了结构化消息带来的KV Cache优化和模型能力提升。  
    可能实现了一个非标准化的工具调用循环，在格式解析和错误处理上存在各种边界情况的bug。  
- 工具设计的不规范  
    工具定义时，过于简略、缺少使用边界说明、参数缺乏具体示例
- 技术选型的滞后性  
    使用过时的技术栈  
    选择较旧的模型、使用旧接口
- 外部生态的脱节   
    可能使用需要付费注册的API   
    可能使用已经废弃的API   
    可能引用不再维护的库或者陈旧的库版本  
    可能采用已被证明有缺陷的模式  

解决以上问题的最有效路径，不是试图在提示词中穷尽所有规则，而是提供一个高质量的Agent实现作为参考范例，并引导代码生成Agent在此基础上进行修改而非从零开始。
