### 协作工具
- 通过调用专门的Sub-Agent,它可以将特定领域的任务委托给更专业的Agent
- 在关键决策点,它知道何时需要请求人类的介入和确认
- 在多Agent系统中,它能够与其他Agent交换信息、协调行动     

这种协作能力让Agent不再是孤立的个体，而是智能网络中的一个节点。   

## 感知工具
### 工具整合
判断工具是否应该整合？   
- 如果多个工具处理的是同类输入、产生同类输出、在相似场景下被调用，那么就应该整合为一个工具。  
    **举例**：文档处理时可能有`extract_pdf_text`、`extract_docx_content`、`extract_pptx_content`等多个独立工具。这些工具的共性在于：都是从文档文件中提取文本内容，输入是文件路径，输出是文本字符串。更好的设计是提供一个统一的`read_document`工具，通过`file_type`参数来区分不同的文档格式。
- 如果功能相似但参数差异很大、或者某个特定功能使用频率极高，那么保持工具独立可能更合理。   
    **举例**：虽然图片和视频都是多媒体内容，但图片解析（OCR、AI分析）和视频解析（关键帧提取、时长分析）的参数和返回结果差异显著，所以这两工具最好保持独立。

### 工具描述 
- **明确的功能说明**：工具能做什么，什么时候用    
- **清晰的使用边界**：什么时候能用，什么时候不能用
- **具体的使用示例**
- **精确描述输出格式**：工具返回什么样的数据结构
- **性能和成本提示**：某些工具执行可能比较耗时间或计算资源，在描述中提醒Agent

### 工具组织
一种有效的组织方式是**按照信息源的性质分类**：
- 搜索工具：用于主动查找信息，如网络搜索、知识库搜索、文件搜索
- 读取工具：从已知位置提取内容，如网页阅读、文档读取、数据查询
- 解析工具：处理和理解非结构化数据，如图片OCR、视频分析、音频转录
- 查询工具：访问结构化数据源，如天气API、股票API、公开数据库   

因此，当Agent
- 当需要"找到某个信息"时，它会首先考虑搜索工具
- 当已经知道了信息源的位置，需要"获取内容"时，它会转向读取工具
- 当内容是多媒体格式需要"理解"时，它会使用解析工具。    

在工具描述的提示词中，可以显式地说明这种分类结构，帮助LLM快速定位到相关工具组，而不要扫描整个工具列表。   

## 执行工具

与感知工具不同，执行工具的错误代价可能极高：误删的文件无法恢复，错误的系统命令可能导致服务中断，不当的API调用可能产生真实的财务损失。因此，执行工具的设计需要在**能力开放**和**安全约束**之间取得微妙的平衡。    

### 安全机制的层次化设计  
- 输入验证：验证所有参数的合法性，比如   
    - 文件路径参数，检查是否存在路径遍历攻击   
    - 命令参数，检查是否包含注入风险（如通过分号或管道符拼接额外命令）
    - API调用参数，验证数据类型和格式是否符合规范  
- 权限控制：检查当前操作是否在允许的权限范围内  
    - 文件操作工具，应该限制只能访问特定的工作目录
    - 命令执行工具，应该维护一个禁止命令的黑名单
    - 外部API工具，应该检查配额和速率限制 


### 双模型决策机制  
让两个独立的模型对同一个决策进行评估，一个模型负责提议行动，另一个模型负责审查批准。    
- 提议模型   
    强调行动导向和任务完成
- 审批模型     
    强调风险控制和规则遵守   

### 自动验证与反馈闭环  
如果操作结果可以被验证，就应该自动验证。以代码编写为例，当Agent调用工具创建或修改代码文件时，工具不应该只是简单地写入内容后返回成功。更好的设计是在写入后立即执行以下验证流程：  
1. 语法检查：根据文件类型调用相应的linter或者语法检查器
2. 结果解析：将linter的输出解析为结构化的错误或者警告列表
3. 反馈生成：将验证结果作为工具调用的返回值的一部分返回Agent    

这种设计创建了一个"执行-验证-反馈"的闭环。

## 协作工具

### Sub-Agent的设计哲学
Sub-Agent机制允许主Agent将特定子任务委托给专门的Agent。  
- 角色定义要清晰   
- 上下文来源要明确标注
    - 主Agent的指令
    - 其他Sub-Agent的返回结果
    - 用户的直接输入
    - 工具的执行输出
- 任务边界要明确界定   
    Sub-Agent应该清楚知道什么在其职责范围内，什么需要转交给其他Agent或上报给主Agent   
- 输出格式要标准化   

### Sub-Agent上下文的准备  
- 最小化传递    
    Sub-Agent只接收主Agent明确传递的调用参数，如"查询订单号12345状态"。但如果用户之前提到过"我在美国"，而查询订单需要知道地区信息，Sub-Agent就无法获取上下文。   
- 手动筛选传递   
    主Agent在调用时显式指定要共享的上下文信息。如：调用参数不仅包含"查询订单号12345"，还包含"用户所在地区：美国"，"对话摘要：用户询问退款政策"。这需要主Agent的提示词明确说明如何筛选和选择上下文，或者由工具的参数设计引导LLM主动提供必要的上下文。   
- 自动裁剪传递  
    系统配置"Sub-Agent自动接收：用户的基本信息（姓名、地区、语言偏好）+最近3轮对话+相关的工具调用结果"。这相当于对主Agent的轨迹做结构化裁剪和压缩后，作为Sub-Agent的初始上下文。
- LLM生成上下文  
    系统调用一个额外的LLM，输入包括：   
    - 主Agent的完整或部分轨迹
    - 业务规则Prompt（描述什么样的信息应该传递给Sub-Agent，什么信息应该过滤）
    - Sub-Agent的类型和任务描述  
    LLM根据这些输入生成一个结构化的上下文对象。   

实践中，可以根据Sub-Agent的类型和任务复杂度选择不同的策略：   
- 最小化传递   
    适用于简单的、高频的Sub-Agent调用，如查询天气、计算器
- 自动裁剪传递  
    适用于中等复杂度的任务
- LLM生成上下文   
    适用于需要丰富上下文的复杂任务，如生成报告、客户服务 

### Agent间的协作机制  
查询订单信息（客服Agent） → 处理退款请求（退款Agent）  

- 同步调用
- 异步调用      
    允许主Agent在等待Sub-Agent的同时继续工作。  
    主Agent发起调用后，立即获得一个"任务ID"或者"承诺（Promise）"，然后可以继续处理其他事情。   
    当Sub-Agent完成任务时，通过通知事件通知主Agent，主Agent在合适的时机处理返回结果。
- 流式协作     
    一个「数据分析Agent」调用「报告生成Agent」，希望在报告生成过程中逐步接收结果，向用户展示进度。  
    Sub-Agent在处理过程中多次发送增量消息，每次携带部分结果或者进度信息。   
    主Agent收到这些增量消息，可以选择立即向用户展示，或者累积后一次性处理。

---

> **理解用（非正文）**：异步调用 vs 流式协作  
> 两者都涉及「不必干等 Sub-Agent」，但回答的是不同维度的问题，且可叠加使用。
>
> **一句话区分**
>
> | | 异步调用 | 流式协作 |
> |---|---|---|
> | 核心问题 | **什么时候**拿回控制权？ | **结果怎么**传回来？ |
> | 典型交付 | 完成时 **一次** 给完整结果 | 处理中 **多次** 给增量/进度 |
> | 主 Agent 常见行为 | 先去做别的事，稍后再处理 | 边收边展示或边收边处理 |
>
> **异步调用**：解决的是「阻塞 / 并行」
>
> - 发起后立刻拿到任务 ID / Promise，主 Agent 继续做别的事。
> - Sub-Agent 完成后，通过 **一次通知** 交付 **完整结果**。
> - 类比：点了一道需炖 2 小时的菜，拿到取餐号后可先吃凉菜；菜好了 **叫号一次**，端走整盘。
> - 客服 → 退款：先回复「已受理」，后台跑完后再 **一次** 回调成功/失败。通常不关心中间审了几步。
>
> **流式协作**：解决的是「增量交付 / 体验」
>
> - Sub-Agent **处理过程中多次** 发消息，每次带部分结果或进度。
> - 主 Agent 可立即展示，或先累积再处理。
> - 类比：做菜时从传菜窗 **逐盘递出**，边做边看进度，而非等全席上完。
> - 数据分析 → 报告：「汇总中…」「第 1 章…」「第 2 章…」，用户不必干等整份报告。
>
> **正交关系（可叠加）**
>
> ```
>                     一次性返回完整结果          多次返回增量
>                  ┌─────────────────────┬─────────────────────┐
>   主Agent阻塞等待 │  同步调用（普通RPC）  │  同步 + 流式          │
>                  ├─────────────────────┼─────────────────────┤
>   主Agent不阻塞   │  异步调用（后台任务）  │  异步 + 流式          │
>                  └─────────────────────┴─────────────────────┘
> ```
>
> - **异步**：主 Agent **时间上** 是否被这次调用占住。
> - **流式**：结果 **结构上** 是一次性还是分块。
> - 只做异步、不流式：后台跑完，通知一次「退款成功」。
> - 只做流式、不异步：主 Agent 仍挂着调用，但边收 token/段落边展示（如 ChatGPT 打字效果）。
> - 异步 + 流式：后台长任务，期间多次推进度（30% → 60% → 完成）。
>
> **选型速记**
>
> - 任务要跑很久，主 Agent **还有别的事** → 优先 **异步**。
> - 用户需要 **进度条、打字机效果、边生成边读** → 优先 **流式**。
> - 既要后台跑、又要中途更新用户 → **异步 + 流式**。


### Human-in-the-loop的艺术   

- 超时和降级策略  
    human-in-the-loop请求可能不会立即得到响应——人类可能正在忙碌或不在线。Agent应该有应对机制。    
    - 设置超时阈值和默认行为。  
        如果5分钟内没有人类响应，采用保守策略（取消操作/选择最安全的选项）
    - 引入优先级队列  
        紧急请求通过多渠道（邮件+短信+IM），普通请求只发邮件，并继续处理其他任务   
- 反馈循环的建立  
    human-in-the-loop不应该是一次性的交互，而应该形成学习循环。当人类批准或拒绝某个决策时，记录这个判断及理由。随着时间积累，系统可以分析这些历史数据，发现人类决策的模式，逐步提高Agent的自主判断能力，减少未来的human-in-the-loop需求。   
    **后训练**是最直接的方式——将积累的human-in-the-loop交互数据（包括决策情境、Agent的初步判断、人类的最终决策和理由）构建为监督学习**数据集**，通过**微调**使模型内化这些决策模式。这种方法特别适合那些反复出现的标准化决策场景，如"涉及金额超过X元的退款必须人工审批"、"修改系统配置文件前必须备份"等规则性知识。  
- 外部学习
    将human-in-the-loop决策案例以结构化的形式存储在**知识库**中，每个案例包含情境描述、决策问题、人类判断、决策依据等信息。当Agent面临新的决策时，通过检索相似的历史案例类辅助判断。
