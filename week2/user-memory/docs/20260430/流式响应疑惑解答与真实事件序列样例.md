# stream=True 流式响应疑惑解答与真实事件序列样例

本文档用于集中回答以下两个核心疑问：

- 如何判断流式响应什么时候结束
- 为什么必须把 `content/reasoning/tool_calls` 按当前代码方式做分通道拼接

---

## 1. 先给一个稳定心智模型

把 `stream=True` 理解成“分包快递”：

- 非流式：模型一次性返回完整消息
- 流式：模型把同一条消息拆成很多小块（`chunk`）依次返回

你的代码在做的事情就是：边收边拼，最后组装完整 assistant 消息。

---

## 2. 流式响应什么时候结束

在当前实现中，结束条件很简单：

- `for chunk in stream:` 还在迭代 -> 响应还没结束
- `for` 循环自然退出 -> 这一轮流式响应结束

也就是说，在 SDK 层你不需要手动判断“最后一块是哪一块”，循环跑完就是结束信号。

---

## 3. 流式过程中每块可能给你什么

每个 `chunk` 的 `delta` 都可能只包含以下字段中的一部分（甚至为空）：

- `delta.content`：普通文本片段
- `delta.reasoning`：推理片段（部分模型支持）
- `delta.tool_calls`：工具调用片段

关键：`tool_calls` 往往不是一次完整返回。  
同一个调用的 `id/name/arguments` 可能分多块到达，且多个调用可能交错到达。

---

## 4. 为什么必须“分通道 + 按 index 拼接”

当前代码采用三条缓冲通道：

- `collected_content`：拼普通文本
- `collected_reasoning`：拼推理文本
- `current_tool_calls`：拼工具调用对象

其中 `current_tool_calls` 还需要按 `tool_call_delta.index` 定位，因为：

- 同一轮可同时出现多个工具调用（`index=0,1,2...`）
- 每个调用的字段会被拆碎后多次到达

如果不按 `index` 拼接，会把不同工具调用的数据串在一起，导致 `arguments` 错位或 JSON 破坏。

---

## 5. 真实事件序列样例（逐 chunk）

下面是一个“看起来很真实”的事件流。目标是生成：

- `tool_calls[0]`: `add_memory({"content":"A"})`
- `tool_calls[1]`: `add_memory({"content":"B"})`

### 初始状态

```text
collected_content = []
collected_reasoning = []
current_tool_calls = []
```

### Chunk 1

```text
delta.tool_calls = [{ index: 0, id: "call_0" }]
```

处理后：

```text
current_tool_calls[0] = { id:"call_0", type:"function", function:{name:"", arguments:""} }
```

### Chunk 2

```text
delta.tool_calls = [{ index: 1, id: "call_1" }]
```

处理后：

```text
current_tool_calls[1] = { id:"call_1", type:"function", function:{name:"", arguments:""} }
```

### Chunk 3

```text
delta.tool_calls = [{ index: 0, function: { name: "add_memory" } }]
```

处理后：

```text
current_tool_calls[0].function.name = "add_memory"
```

### Chunk 4

```text
delta.tool_calls = [{ index: 1, function: { name: "add_memory" } }]
```

处理后：

```text
current_tool_calls[1].function.name = "add_memory"
```

### Chunk 5

```text
delta.tool_calls = [{ index: 0, function: { arguments: "{\"content\":\"A" } }]
```

处理后（注意是 `+=`）：

```text
current_tool_calls[0].function.arguments = "{\"content\":\"A"
```

### Chunk 6

```text
delta.tool_calls = [{ index: 1, function: { arguments: "{\"content\":\"B" } }]
```

处理后：

```text
current_tool_calls[1].function.arguments = "{\"content\":\"B"
```

### Chunk 7

```text
delta.tool_calls = [{ index: 0, function: { arguments: "\"}" } }]
```

处理后：

```text
current_tool_calls[0].function.arguments = "{\"content\":\"A\"}"
```

### Chunk 8

```text
delta.tool_calls = [{ index: 1, function: { arguments: "\"}" } }]
```

处理后：

```text
current_tool_calls[1].function.arguments = "{\"content\":\"B\"}"
```

### Chunk 9（可选）

```text
delta.content = "我已记录两条记忆。"
```

处理后：

```text
collected_content = ["我已记录两条记忆。"]
```

### 流结束（for 循环退出）

最终组装：

```text
complete_message = {
  "role": "assistant",
  "content": "我已记录两条记忆。",
  "tool_calls": [
    {id:"call_0", type:"function", function:{name:"add_memory", arguments:"{\"content\":\"A\"}"}},
    {id:"call_1", type:"function", function:{name:"add_memory", arguments:"{\"content\":\"B\"}"}}
  ]
}
```

随后进入工具执行阶段，逐条 `json.loads(arguments)` 并执行，再把结果追加为 `role="tool"` 消息。

---

## 6. conversation 中会出现哪些消息

典型序列是：

1. `system`
2. `user`
3. `assistant`（可能仅 `tool_calls`，`content` 为 `None`）
4. `tool`（每个工具调用一条）
5. 下一轮 `assistant`（基于工具结果继续）

因此并不是“只有 `system/user/assistant` 三种角色”，`tool` 在该链路里是必需角色。

---

## 7. 常见误解与纠偏

- 误解：每个 chunk 都应该有完整 JSON  
  纠偏：chunk 是增量片段，天然可能不完整

- 误解：有了 `tool_calls` 就不会有 `content`  
  纠偏：同一轮中可能同时出现（取决于模型行为）

- 误解：看到多条 `add_memory` 就是代码重复调用  
  纠偏：通常是模型主动规划多次调用，这是预期行为

- 误解：流结束要靠自己猜最后一块  
  纠偏：在当前 SDK 用法里，`for chunk in stream` 结束即流结束
