# Context Compression 项目机制总结

## 1. 程序整体运行链路

1. 在 `main.py` 中选择压缩策略（1~6）。
2. 创建 `ResearchAgent`，并将所选策略传入。
3. Agent 调用主模型进行推理，决定是否发起工具调用（`search_web` / `fetch_webpage`）。
4. 工具执行后，结果写回对话历史，再次发送给主模型进入下一轮，直到产出最终答案或达到迭代上限。

---

## 2. 不同压缩策略是如何生效的

压缩策略由 `CompressionStrategy` 枚举定义，并在 `ContextCompressor.compress_search_results()` 里按策略分发到不同实现函数。

### 2.1 `no_compression`（策略 1）

- 不做摘要压缩。
- `search_web` 返回结果会基本原样（JSON）放入对话历史。
- 随着工具结果增多，上下文会迅速膨胀，容易触发高 token 消耗。

### 2.2 `context_aware_summary`（策略 4）

- 会先对每个网页内容做长度限制（每页最多约 `5000` 字符）。
- 然后把截断后的多页内容拼接成一个 prompt。
- 压缩提示词中显式包含两类上下文锚点：`search query`（当前查询意图）和 `current context`（已有信息摘要）。
- 通过把 `query` 与 `current_context` 放入提示词，引导模型做“问题导向”的信息筛选，而不是泛化总结。
- 再调用模型生成“面向 query 的聚焦摘要”。
- 最后把摘要（而不是原始长网页内容）写回对话历史，从而缩小上下文。

> 结论：这不是“只截断”而是“截断 + 模型摘要”两步压缩。

### 2.3 与工具类型的关系

- 当前实现中，压缩主要作用于 `search_web` 的结果。
- `fetch_webpage` 的返回在 `_execute_tool()` 中默认不压缩（返回 `compressed=None`）。

---

## 3. 工具机制说明

## 3.1 模型可调用的工具

`agent.py` 通过 tools/function schema 暴露两类工具：

- `search_web(query, num_results)`
- `fetch_webpage(url)`

主模型根据当前对话状态自行决定是否发起工具调用（`tool_choice="auto"`）。

## 3.2 `search_web` 用的是什么搜索能力

- 使用的是 **Serper API**（`https://google.serper.dev/search`），不是直接调用 Google 官方 Search API。
- Serper 会返回搜索结果列表（标题、链接、摘要等）。
- 程序随后会对结果链接逐个抓取网页正文。

## 3.3 `fetch_webpage` 的处理流程

- 使用 `requests.get` 抓取网页。
- 用 `BeautifulSoup` 清理页面结构（去脚本、样式等）。
- 用 `html2text` 转成文本。
- 超长文本按配置截断，并做缓存以减少重复抓取。

---

## 4. “完成任务模型”和“摘要模型”是不是两个模型？

从职责上看，是两次独立模型调用：

- `ResearchAgent`：主任务推进、工具决策、整合答案。
- `ContextCompressor`：对网页内容做摘要压缩。

但从当前代码配置看，二者通常使用同一个模型名（都来自 `Config.MODEL_NAME`），因此默认是**同一模型在不同阶段被调用**，而不是天然的“双模型架构”。

如果需要，也可以扩展为：

- 主任务模型（高推理能力）
- 摘要压缩模型（更低成本）

以进一步优化成本与效果平衡。

---

## 5. 关于 `tiktoken` 的结论

- `compression_strategies.py` 中的 `import tiktoken` 来自 Python 环境中的第三方包（`site-packages`），不是项目内置模块。
- 是否能导入，取决于当前解释器环境是否安装该包，而不是“是否只打开了某个目录”。
- 已将 `tiktoken>=0.7.0` 补充到 `week2/context-compression/requirements.txt`，避免新环境缺包。
